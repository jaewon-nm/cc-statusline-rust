# 005 — `install` / `uninstall` subcommands

**Status:** active · Codex-AGREE (round 4) · **Owner:** jaewon_lee · **Opened:** 2026-05-14 · **Last revision:** 2026-05-14

## Goal

Eliminate the manual three-step setup (copy binary → write `.mjs` wrapper → patch `~/.claude/settings.json`) discovered during M5 by shipping it as two declarative subcommands:

```
ccstatusline-rs install   [--bin-dir <path>] [--settings <path>] [--force]
ccstatusline-rs uninstall [--settings <path>] [--backup <path>] [--bin-dir <path>] [--purge-binary]
```

Both emit JSON on stdout per the agent contract, fail fast on typed errors, and never mutate config without a timestamped backup.

## Why now

- M5 wired the renderer into Claude Code by hand. We discovered Claude Code on Windows refuses bare `.exe` and `cmd /c`-wrapped commands — only the `<interpreter> <script>` shape (e.g. `node "...mjs"`) is honored. Every install on Windows therefore needs a small `.mjs` shim.
- Users who follow `INSTALL.md` today have to copy the binary, hand-write the wrapper, and edit JSON. That's three places to forget a backslash and one place to clobber working config.
- Auto-update + rollback are unhealthy without a stable backup convention. `uninstall` makes the rollback a single command.

## Non-goals

- **No PATH manipulation.** The subcommand drops the binary under `~/bin` (Windows) or `~/.local/bin` (POSIX). Adding to PATH is the user's call — we just place the file. The wrapper / settings entry uses an absolute path so PATH is irrelevant for the renderer.
- **No service registration.** Claude Code spawns the binary per refresh; we don't need WinSW / launchd / systemd.
- **No global `cargo install` integration.** Users who reach the binary via `cargo install` are already on `PATH` and can run `ccstatusline-rs install` from there. The subcommand still re-copies to the bin dir to decouple from the user's cargo cache.
- **No removal of the binary on `uninstall` by default.** Reinstall is the common case; deletion is gated behind `--purge-binary`.

## Phase A — surface design

### A.1 CLI

`Command::Install` (new top-level variant of `Cli::Command`):

| Flag | Meaning | Default |
|---|---|---|
| `--bin-dir <path>` | Where to place the binary (and wrapper, on Windows). | `~/bin` on Windows, `~/.local/bin` on POSIX. |
| `--settings <path>` | Override the Claude Code settings file. | `~/.claude/settings.json`. |
| `--force` | Overwrite the dest binary even when it exists and matches. | `false`. |

`Command::Uninstall`:

| Flag | Meaning | Default |
|---|---|---|
| `--settings <path>` | Override settings target. | `~/.claude/settings.json`. |
| `--backup <path>` | Use this specific backup. | Latest `settings.json.ccstatusline-rs-bak-*` next to `--settings`. |
| `--bin-dir <path>` | Where the installed binary and wrapper live (only consulted with `--purge-binary`). | `~/bin` on Windows, `~/.local/bin` on POSIX. |
| `--purge-binary` | Also delete the installed binary and wrapper. | `false`. |

### A.2 Behavior — `install`

1. Resolve `dest_exe`. Source = `std::env::current_exe()`. Dest filename = `ccstatusline-rs.exe` (Windows) or `ccstatusline-rs` (POSIX).
2. Ensure `bin_dir` exists (`fs::create_dir_all`).
3. **Copy binary** to `dest_exe`. Skip when `src == dest`. When dest already exists and `--force` is absent, compare via `xxh3_64` of contents to decide a no-op vs a copy. The Cargo binary may carry build metadata that flips bytes between targets; a quick hash check avoids needless writes during dev loops.
4. **Wrapper.** On Windows, write `ccstatusline-rs.mjs` next to the exe (always `\n`-line-ended; Node on Windows is happy with LF and tests stay stable):
   ```js
   import { spawn } from 'node:child_process';
   const child = spawn(<EXE_JSON_LITERAL>, [], { stdio: ['inherit', 'inherit', 'inherit'] });
   child.on('exit', code => process.exit(code ?? 1));
   child.on('error', err => { console.error(err); process.exit(1); });
   ```
   `<EXE_JSON_LITERAL>` is generated by `serde_json::to_string(&exe_path_str)` — that gives us a correctly-escaped JS string literal (handles backslashes and non-ASCII unicode). The `code ?? 1` (not `?? 0`) preserves signal-termination semantics: a child killed by `SIGTERM` exposes `code === null` and we want the wrapper's exit code to reflect failure, not success. On POSIX, no wrapper is written (Claude Code accepts a bare absolute path on macOS/Linux per the Issue #31670 thread).
5. **Settings.** Read `~/.claude/settings.json` if it exists; otherwise start from `{}`. If it exists, `fs::copy` to `settings.json.ccstatusline-rs-bak-<YYYYMMDD-HHMMSS>-<NNN>` *first*, before any modification (counter rule in [B.4](#b4-backup-naming)).
6. Mutate the parsed JSON in memory:
   ```jsonc
   "statusLine": {
     "type": "command",
     "command": "<wrapper-or-exe-shell-command>"
   }
   ```
   - Windows command string: `node "<wrapper-absolute-path>"` (wrapper path is JSON-string-escaped when serialized; backslashes survive intact).
   - POSIX command string: single-quote escaped per POSIX shell rules — `'<exe-absolute-path>'` with any literal `'` rewritten as `'\''`. Single quotes neutralize `$`, backticks, and backslashes that double-quotes would still interpret. Helper: `fn posix_shell_quote(s: &str) -> String`.
   - All other top-level keys (`env`, `hooks`, `enabledPlugins`, `theme`, …) preserved untouched. Implementation note in [B.5](#b5-json-mutation-rule) for how.
7. Atomic write: `serde_json::to_vec_pretty(&settings)` → `<settings>.tmp` → `fs::rename`.
8. Emit JSON:
   ```jsonc
   {
     "installed": true,
     "bin": "...",
     "wrapper": "..." | null,
     "settings": "...",
     "backup": "..." | null,         // null only when settings file did not exist
     "copied_binary": true | false,
     "previous_command": "..." | null  // whatever statusLine.command was before, for audit
   }
   ```

### A.3 Behavior — `uninstall`

1. Resolve `--settings`.
2. Resolve backup: explicit `--backup` wins; otherwise scan the parent dir for `settings.json.ccstatusline-rs-bak-*` and pick the highest filename (fixed-width timestamp + counter → lex sort matches chronology). No backup found → `Error::NoBackupFound { settings }` with non-zero exit.
3. Restore atomically: `fs::read(backup)` → `ioutil::atomic_write_bytes(settings, &bytes)` (see [B.6](#b6-atomic-write--both-directions)). Plain `fs::copy` is not used.
4. With `--purge-binary`: best-effort remove `<bin-dir>/ccstatusline-rs.exe` (or `ccstatusline-rs`) and `<bin-dir>/ccstatusline-rs.mjs`. Failure to remove is **not** fatal — report each path's outcome in the JSON.
5. Emit JSON:
   ```jsonc
   {
     "uninstalled": true,
     "settings": "...",
     "restored_from": "...",
     "removed": ["...", "..."]   // empty unless --purge-binary
   }
   ```

### A.4 Error surface

Two new typed variants on `error::Error`:

```rust
#[error("file operation '{operation}' failed for {path:?}: {source}")]
FileIo {
    operation: &'static str,
    path: std::path::PathBuf,
    #[source]
    source: std::io::Error,
},

#[error("backup not found alongside {settings:?}")]
NoBackupFound { settings: std::path::PathBuf },
```

`FileIo` is shared by both install and uninstall (and any other future filesystem-touching subcommand) so the message stays operation-neutral.

`operation` is a fixed set of `&'static str` tokens (`"copy_binary"`, `"write_wrapper"`, `"backup_settings"`, `"write_settings"`, `"restore_backup"`, `"purge_file"`, `"mkdir"`). The existing `Stdin(#[from] io::Error)` stays — it's the only place we want a free `?` conversion. Install code does **not** use `?` to convert `io::Error` to `Stdin`; every fallible filesystem call goes through a small helper `fileio!(op, path, expr)` macro that wraps the result. Reusing `Stdin` for install would mask the actual operation that failed and confuse downstream error matching. Reuse `Error::InvalidConfig { reason }` only for malformed settings JSON (we already do this in `config::load_from_or_default`).

## Phase B — implementation

### B.1 Module shape

New file `src/cli/install.rs` containing:

- `pub fn install(args: InstallArgs) -> Result<InstallReport>`
- `pub fn uninstall(args: UninstallArgs) -> Result<UninstallReport>`
- Private helpers: `resolve_bin_dir`, `resolve_settings_path`, `backup_settings`, `read_settings_or_empty`, `compose_command`, `find_latest_backup`, `write_wrapper`, `atomic_write_json`.

`InstallArgs`, `UninstallArgs` — bare structs with `Option<PathBuf>` fields; populated from the new clap variants. `InstallReport` / `UninstallReport` — serde-able structs the dispatcher hands to `emit_value`.

### B.2 CLI wiring

`src/cli/mod.rs` gains two new `Command` variants and dispatch arms. Both dispatch into `install.rs`.

### B.3 Path resolution

Use `directories::BaseDirs::new()`:

- `home_dir()` for both Windows and POSIX home.
- Windows bin: `home_dir.join("bin")` (matches the convention we already use).
- POSIX bin: `home_dir.join(".local/bin")`.
- Settings: `home_dir.join(".claude/settings.json")`.

`std::env::current_exe()` for the source binary. Canonicalize both source and dest before comparison so `target/release/ccstatusline-rs.exe` and the same path through a symlink don't trigger a no-op miss.

### B.4 Backup naming

Filename: `<settings-file-name>.ccstatusline-rs-bak-<YYYYMMDD-HHMMSS>-<NNN>`. Concretely, given `settings.json`, the backup is `settings.json.ccstatusline-rs-bak-20260514-140312-000`. The trailing 3-digit counter is **always present** (000-padded), incremented from `000` upward until a name that doesn't exist on disk is found. This handles back-to-back installs in the same wall-clock second without ever overwriting an existing backup. Lexicographic sort still matches chronological order because every component is fixed-width.

### B.5 JSON mutation rule

`statusLine` is the only key we own. All other top-level keys pass through unchanged. We do **not** enable `serde_json/preserve_order` — that would churn snapshot tests across the rest of the project for no real-world benefit (neither neo-mem nor Claude Code reads key order from this file).

Approach: define a small typed struct just for the install / uninstall reader:

```rust
#[derive(Debug, Serialize, Deserialize, Default)]
struct ClaudeSettings {
    #[serde(default, rename = "statusLine", skip_serializing_if = "Option::is_none")]
    status_line: Option<StatusLine>,
    #[serde(flatten)]
    extra: serde_json::Map<String, serde_json::Value>,
}

#[derive(Debug, Serialize, Deserialize)]
struct StatusLine {
    #[serde(rename = "type")]
    kind: String,
    command: String,
}
```

The `rename = "statusLine"` is load-bearing — Claude Code emits camelCase, our field is snake_case to keep the Rust side idiomatic.

`#[serde(flatten)]` carries every unrecognized top-level key through round-trip without us owning a schema for it. Order within the rest of the document falls back to `BTreeMap` order; tests assert on the *value subtree* (parsed `Value`), not on the byte string. The `statusLine` block re-serializes with `type` first, `command` second because struct field order is preserved by `serde_derive`.

### B.6 Atomic write — both directions

`atomic_write_json(path, value)`:

1. Serialize pretty.
2. Write to `<path>.tmp` (same parent dir → same volume → rename is atomic).
3. `fs::rename(tmp, path)`.

Extract `crate::ioutil::atomic_write_bytes(path, &[u8])` once and reuse it from `Config::save`, install, and uninstall. Temp filename uses a process-id + monotonic counter suffix (`<basename>.tmp.<pid>.<seq>`) so two concurrent installs into the same directory don't race on a fixed `.tmp` name. Both directions matter — **`uninstall` must use the same atomic pattern** when restoring the backup, not a raw `fs::copy(backup, settings)`. A failed restore mid-write would leave Claude Code reading a corrupt file. Path:

```rust
let bytes = fs::read(&backup).map_err(...)?;
ioutil::atomic_write_bytes(&settings, &bytes).map_err(...)?;
```

(`copy` is not atomic on Windows for files larger than the OS write-cache flush size; rename is.)

## Phase C — tests

### C.1 Pure helpers, both platforms

Extract platform-deciding logic behind a small enum so it's testable on every CI runner:

```rust
pub enum Platform { Windows, Posix }

fn compose_command(platform: Platform, exe: &Path, wrapper: Option<&Path>) -> String { ... }
fn wrapper_path(platform: Platform, bin_dir: &Path) -> Option<PathBuf> { ... }
fn wrapper_body(exe: &Path) -> String { ... }
```

Unit tests in `src/cli/install.rs#tests` run on every OS:

- `compose_command_windows_uses_node_wrapper` — `compose_command(Windows, exe, Some(wrapper))` exactly `node "<wrapper>"`.
- `compose_command_posix_single_quotes_exe_path` — `compose_command(Posix, exe, None)` returns `'<exe>'` (single-quote shell escaping per A.2 step 6). Embedded `'` in the path becomes `'\''`. Inputs covered: plain ASCII path, path with space, path containing a literal `'`.
- `wrapper_body_escapes_unicode_paths` — `wrapper_body` over a path with a Korean segment produces a `.mjs` whose JS literal parses back to the same path.
- `wrapper_body_uses_lf_line_endings` — output contains no `\r`.
- `wrapper_body_exits_one_on_signal` — output contains `?? 1` (regression-guarded against a future careless edit to `?? 0`).

### C.2 Integration cases

`tests/install_uninstall.rs` — pins `--bin-dir` and `--settings` to per-test `tempfile::tempdir()`, parallel-safe.

| Case | What it asserts |
|---|---|
| `install_fresh_writes_binary_and_settings` | No prior settings → JSON `backup: null`, `installed: true`; binary present at dest; on Windows, wrapper present. |
| `install_preserves_unrelated_settings_keys` | Existing `env`, `hooks`, `enabledPlugins`, `theme` survive a *parsed-Value* comparison (no byte-level snapshot). |
| `install_idempotent_no_force` | Second call without `--force` returns `copied_binary: false` and does not rewrite the wrapper. |
| `install_force_overwrites` | Second call with `--force` returns `copied_binary: true`. |
| `install_records_previous_command` | Prior `statusLine.command` = `node "...tokenwatch..."` → output `previous_command` carries it verbatim. |
| `install_back_to_back_counter_bumps` | Two installs within a second produce backups suffixed `-000` and `-001` (no overwrite). |
| `uninstall_restores_backup_atomically` | After install → uninstall, settings parsed-Value matches the pre-install Value. Backup file remains on disk afterwards. |
| `uninstall_fails_when_no_backup` | Clean dir → non-zero exit; stderr contains a `NoBackupFound`-style message naming the settings path. (No JSON envelope on stdout — see Phase D / Risk #6 about the global envelope contract being deferred.) |
| `uninstall_purge_binary_removes_files` | With `--purge-binary --bin-dir <tmp>`: exe + mjs gone; JSON `removed` lists both. |
| `uninstall_purge_binary_skips_unrelated_files` | A `sibling.txt` next to our binary in `bin_dir` is **not** deleted. |
| `install_then_uninstall_roundtrip_preserves_unknown_keys` | Roundtrip integrity: install → uninstall → final settings Value equals pre-install Value with `extra` keys intact. |

The two platform-string assertions (`compose_command_*`) are unit tests in C.1, so the integration matrix doesn't need `#[cfg(target_os = …)]` gating. Integration tests that touch the OS filesystem will, on the current platform, exercise either the wrapper-writing branch (Windows) or the bare-exe branch (POSIX). The opposite branch is covered by the pure helpers.

## Risks & open questions

1. **Decision: don't enable `serde_json/preserve_order`.** We considered flipping `Map<String, Value>` from `BTreeMap` to `IndexMap` for original-order preservation. Rejected (Codex round 1 #1): the only consumer that cares about top-level order is a human reading the file, and the `#[serde(flatten)] extra` path keeps unknown keys alive without that complexity. `Config` already serializes via struct field order, not map order, so existing snapshot tests are unaffected. Logged here so a future contributor doesn't re-litigate.
2. **Settings file owned by another tool.** neo-mem also writes `statusLine`. If the user uninstalls *us* while neo-mem has overwritten the file since our backup, restoring our backup clobbers neo-mem's edits. **Mitigation:** `uninstall` JSON output includes `restored_from` so the user sees which snapshot. We do not attempt three-way merge.
3. **macOS `.app` codesigning.** A copied binary may trigger Gatekeeper on macOS. We don't sign anything; first run requires the user to allow it manually. Document in INSTALL.md.
4. **Path with non-ASCII characters.** Windows usernames like `홍길동` produce paths that need to round-trip through JSON and JS. `serde_json` handles UTF-8 strings; the `.mjs` template uses `serde_json::to_string(path_str)` to embed the path as a valid JS string literal (B.5 / A.2 step 4). **Mitigation:** unit test the wrapper-string generation against a path with a non-ASCII segment (C.1's `wrapper_body_escapes_unicode_paths`).
5. **Race against a running Claude Code.** Modifying settings while Claude Code is running is fine (atomic rename) — the live process keeps the old config until it re-reads. Document that a restart is needed for the change to take effect; the install JSON's `installed: true` is a *configuration* success, not a *runtime activation* claim.

6. **Global error JSON envelope deferred.** The agent surface contract in `docs/design-docs/cc-statusline-rs.md` calls for `{"error":{"code":"…","message":"…",…}}` on stdout for failures. M5 didn't ship that across all subcommands. For `install`/`uninstall` this milestone, failure paths print to stderr only (anyhow display via `main.rs`) with non-zero exit; the underlying error variants (`FileIo`, `NoBackupFound`) are typed so a future "global envelope" plan can map them deterministically without rewriting this code. Tests assert exit code + stderr substring, not stdout JSON, for failure cases.

## Acceptance

- A single command (`ccstatusline-rs install`) sets up the binary, wrapper (on Windows), and `statusLine` entry from a clean machine.
- A single command (`ccstatusline-rs uninstall`) reverts the *most recent* install (Codex review #4) — i.e. restores the settings file that existed immediately before the last `install` call. Earlier snapshots are reachable through `--backup <path>`.
- Both commands' JSON output is the only stdout content (no banner / no extra newline beyond the trailing one we already emit).
- All listed test cases pass; no `#[ignore]`, no skipped tests.
- Re-running `install` is safe and idempotent.
- `uninstall` restores via atomic write (temp + rename), never via raw `fs::copy`.
